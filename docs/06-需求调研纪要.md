---

## 1. 调研目标

1. 确认“需求管理与交付协同”场景中最高频、最痛的三个问题；
2. 识别不同角色的核心诉求与冲突点；
3. 判断哪些能力必须进入 MVP，哪些可以裁剪；
4. 为需求池、状态机、数据权限和验收标准提供依据。

## 3. 访谈记录

### 3.1 业务提出人（biz）

**现状**

- 需求通过邮件、群聊、Excel 三种方式提出，编号靠人工维护；
- 提交后不知道谁在處理，只能私聊追问；
- 验收时经常发现“做的不是最初说的”，但缺少书面依据。

**关键原话（模拟）**

> “我不怕排队，怕的是提了之后没回音。”
> 
> “每次验收都要翻聊天记录找当时怎么说的。”

**痛点归纳**

1. 需求状态不透明，缺少统一入口；
2. 需求描述没有模板，验收标准经常缺失；
3. 变更没有留痕，口头确认无法追责。

**衍生需求**

- RQ-008 需求单统一入口与编号；
- RQ-009 提交前必填校验（背景、描述、验收标准）；
- RQ-011 状态与进度可查；
- RQ-019 / RQ-020 变更留痕与影响可追溯。

### 3.2 需求分析（ra）

**现状**

- 受理后靠 Word 写规格，版本用文件名区分（`xxx_v2_final.docx`）；
- 评审靠会议，结论记在会议纪要，需求单本身不更新；
- 变更由业务口头提出，开发直接改，基线失控。

**关键原话（模拟）**

> “最怕评审会上说‘这个再议’，会后没人记得再议什么。”
> 
> “同一个需求三个版本，我不知道哪个是开发在做的。”

**痛点归纳**

1. 规格与需求单分离，版本不可追溯；
2. 评审意见与结论没有结构化留痕；
3. 变更没有审批与基线更新机制；
4. 待受理需求分散，缺少统一池子。

**衍生需求**

- RQ-016 评审单与需求快照；
- RQ-017 评审意见与结论；
- RQ-019 变更申请、审批、实施；
- RQ-012 版本快照与版本号；
- RQ-004 待受理池与部门数据权限。

### 3.3 项目经理（pm）

**现状**

- 用 Excel 排期，需求和任务靠人工关联；
- 任务拆分粒度不一致，进度靠周会同步；
- 变更经常影响排期，但工时影响没人评估。

**关键原话（模拟）**

> “我不需要花哨的甘特图，我需要知道哪个任务卡住了。”
> 
> “变更可以提，但要告诉我多花多少工时。”

**痛点归纳**

1. 需求与任务脱节，无法从需求看进度；
2. 缺少任务状态与逾期标识；
3. 变更缺少影响工时与范围记录。

**衍生需求**

- RQ-022 项目与里程碑；
- RQ-023 任务分解、负责人、预估工时；
- RQ-024 任务状态机与逾期标记；
- RQ-020 变更影响工时。

### 3.4 开发与测试（dev / qa）

**现状**

- 需求描述经常缺少边界与非目标，开发靠猜；
- 测试没有明确验收标准，返工原因口头说；
- 开发任务没完成就被催着提测。

**关键原话（模拟）**

> “验收标准写成‘体验良好’，我没法测。”
> 
> “最烦的是提测后才发现还有任务没做完。”

**痛点归纳**

1. 验收标准不可测；
2. 提测缺少准入校验；
3. 返工原因没有记录，重复踩坑。

**衍生需求**

- RQ-009 验收标准必填；
- RQ-011 开发任务全部完成才允许提测（状态机前置校验）；
- RQ-028 验收不通过生成返工任务并记录原因。

### 3.5 验收人与管理员（accept / admin）

**现状**

- 验收材料散落在各人电脑，缺少统一清单；
- 验收结论靠邮件确认，归档后查不到历史；
- 权限靠“谁都能看”，审计靠人工回忆。

**关键原话（模拟）**

> “验收不是签字，是要能说清交付了什么。”
> 
> “出了问题，至少要能查到谁在什么时候改的。”

**痛点归纳**

1. 交付物清单不统一，验收缺少硬性校验；
2. 归档后数据仍可改，历史不可信；
3. 缺少操作审计与数据权限。

**衍生需求**

- RQ-026 交付物登记与必备校验；
- RQ-027 验收单与轮次；
- RQ-029 归档只读；
- RQ-004 数据权限；
- RQ-005 审计日志。

## 4. 调研结论

### 4.1 痛点优先级

| 排名  | 痛点            | 影响角色          | 对应需求                   |
| --- | ------------- | ------------- | ---------------------- |
| 1   | 需求状态不透明、结论无留痕 | 全部            | RQ-008/009/011/016/017 |
| 2   | 变更与版本失控       | RA、PM、DEV     | RQ-019/012/020         |
| 3   | 验收标准不可测、交付物不齐 | biz、QA、accept | RQ-011/026/027         |
| 4   | 越权与审计缺失       | admin、accept  | RQ-004/005/029         |
| 5   | 排期与任务脱节       | PM、DEV        | RQ-022/023/024         |

### 4.2 范围决策

| 决策          | 结论   | 理由                         |
| ----------- | ---- | -------------------------- |
| 是否引入工作流引擎   | 不做   | 状态与角色固定，枚举 + 流转表即可表达       |
| 是否做微服务      | 不做   | 小团队规模，单体收益更高                 |
| 是否做站内通知     | 本期不做 | 用“我的待办”实时查询替代，避免额外表与定时任务   |
| 是否做 Word 导出 | 本期不做 | Excel 导出已能证明导出能力，Word 留作演进 |
| 是否做评论       | 本期不做 | 评审意见已覆盖关键沟通留痕              |
| 是否做两级审批     | 本期不做 | 单级审批足够演示，避免规则膨胀            |
| 是否做多租户      | 不做   | 与目标岗位和项目规模不匹配              |

### 4.3 MVP 边界

MVP 必须闭环：

```
提出 → 受理 → 评审 → 排期 → 任务 → 开发测试 → 交付验收 → 归档
```

支撑能力：登录、RBAC、数据权限、状态机、版本快照、审计、Excel 导出、看板。

### 4.4 假设与待验证

| 假设               | 风险         | 验证方式        |
| ---------------- | ---------- | ----------- |
| 需求量在 10 万以内，单库足够 | 数据量增长后查询变慢 | 压测与索引验证（待补） |
| 多角色取最宽数据范围可接受    | 精细权限场景不满足  | 真实客户访谈（待补）  |
| 主持人单点结论可代表评审结果   | 会签场景不满足    | 标准版补全员会签    |
| 本地磁盘附件可满足演示      | 多实例部署不可用   | 演进为 MinIO   |
| 用户能接受桌面端操作       | 移动场景缺失     | 明确不在范围      |
