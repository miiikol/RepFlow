## 2. 项目概述

### 2.1 业务背景

项目模拟银行、国企信息中心常见的“甲乙方内部交付”场景：业务部门提出需求，科技部门或交付团队负责受理、评审、排期、开发测试和验收。

典型痛点：

1. 需求散落在邮件、即时通讯和 Excel，编号不统一，重复与遗漏并存；
2. 需求缺少可验证的验收标准，评审靠口头确认，结论无法追溯；
3. 变更以聊天记录为准，基线版本混乱，开发、测试、业务理解不一致；
4. 交付物保存在个人电脑，验收缺少统一清单，归档后无法复盘。

### 2.2 项目目标

1. 用一张需求单串起“提出—受理—评审—排期—开发测试—验收—归档”的完整链路；
2. 用状态机约束流转，非法操作被服务端拒绝，而不是靠前端隐藏按钮；
3. 用 RBAC + 数据权限控制“能不能操作”和“能看到哪些数据”；
4. 用审计日志和版本快照回答“谁在什么时间改了什么”；
5. 保持单体架构与零数据库依赖启动，保证可演示、可讲清。

### 2.3 目标用户

| 用户        | 核心诉求                 |
| --------- | -------------------- |
| 业务部门需求提出人 | 需求被及时受理，进度可查，结论可追溯   |
| 需求分析（RA）  | 规格可验证，评审与变更留痕，交付范围可控 |
| 项目经理（PM）  | 计划可执行，任务可跟踪，逾期可识别    |
| 开发/测试     | 任务边界明确，返工原因可查        |
| 验收人       | 交付物齐全，验收有依据          |
| 系统管理员     | 权限可控，操作可审计           |

### 2.4 范围

**本期实现（MVP + 部分标准版）**

- 认证、JWT、账号锁定、RBAC 权限点、四档数据权限；
- 需求单 CRUD、分页筛选、状态机、版本快照、附件；
- 评审单、评审意见、评审结论；
- 变更申请、单级审批、变更实施与版本递增；
- 项目、里程碑、任务分解、任务状态机；
- 交付物登记、验收单、返工任务、归档只读；
- 看板指标、Excel 导出、审计日志查询；
- Flyway 迁移、Docker Compose、CI、自动化测试。

**本期明确不做**

微服务拆分、注册中心、分布式事务、BPMN 工作流引擎、移动端/小程序、真实短信/企微集成、多租户、分库分表、BI 大屏。

原因：与课程小组项目 + 个人 v2 工程化重构的项目预算不匹配，强行加入会牺牲主流程闭环。

## 3. 角色与权限

### 3.1 角色定义

| 角色编码     | 角色    | 职责               | 数据范围        |
| -------- | ----- | ---------------- | ----------- |
| ADMIN    | 系统管理员 | 用户、角色、审计、全局数据    | ALL         |
| BUSINESS | 需求提出人 | 新建、修改草稿、提交、查看进度  | SELF        |
| RA       | 需求分析  | 受理、编写规格、发起评审、归档  | DEPT + 待受理池 |
| PM       | 项目经理  | 排期、任务分解、变更审批     | PROJECT     |
| DEV      | 开发    | 领取任务、更新任务状态、提交测试 | PROJECT     |
| QA       | 测试    | 测试任务、评审意见、提交验收   | PROJECT     |
| ACCEPT   | 验收人   | 提交验收结论           | PROJECT     |

### 3.2 权限模型

采用 RBAC + 数据权限双层模型：

- **功能权限**：38 个权限点，命名形如 `requirement:view`、`review:decide`，后端通过 `@PreAuthorize("hasAuthority('...')")` 校验；
- **动作权限**：状态流转、越权判断、数据权限中的特殊规则全部绑定权限点（如 `requirement:accept`、`requirement:schedule`），角色只作为权限点的集合，调整授权不需要改代码；
- **数据权限**：ALL / DEPT / PROJECT / SELF 四档，由角色配置，多角色取最宽一档；
- **单条校验**：详情、审批、下载等操作在服务层再次校验数据归属，越权返回 `403 / 20002`，不能靠猜 ID 访问。

实现位置：`DataScopeService` 是数据权限的唯一实现，列表、导出、跨表子查询复用同一段谓词。

### 3.3 数据范围规则

| 范围      | 可见规则                                       |
| ------- | ------------------------------------------ |
| ALL     | 全部需求                                       |
| SELF    | 本人提出的需求                                    |
| DEPT    | 本部门需求 + 本人分析的需求 + 待受理池（仅 RA）               |
| PROJECT | 本人任 PM、分析人、任务负责人、验收人、评审参与人的需求，以及本人负责项目下的需求 |

补充规则：无论哪一档，**需求提出人始终可见自己提出的需求**。这是业务规则，不是权限放宽。

## 4. 业务流程

### 4.1 端到端主流程

| 阶段   | 输入        | 输出            | 责任人    | 系统动作                |
| ---- | --------- | ------------- | ------ | ------------------- |
| 需求提出 | 业务背景、期望日期 | 需求单（草稿/待受理）   | 提出人    | 生成 `REQ` 编号，校验必填项   |
| 受理分析 | 需求单、补充材料  | 分析结论、优先级、验收标准 | RA     | 状态转分析中，记录分析人        |
| 评审   | 需求快照      | 评审单与结论        | RA 组织  | 生成 `RV` 编号，回写需求状态   |
| 排期   | 评审通过的需求   | 项目、里程碑、计划日期   | PM     | 关联项目与里程碑            |
| 任务分解 | 已排期需求     | 任务列表与负责人      | PM     | 生成 `TSK` 编号，记录预估工时  |
| 开发测试 | 任务、验收标准   | 开发成果、测试结论、交付物 | DEV/QA | 推进任务状态，校验完成条件       |
| 交付验收 | 交付物清单     | 验收单结论、返工要求    | 验收人    | 校验必备交付物，生成 `ACC` 编号 |
| 归档   | 已验收需求     | 只读记录与快照       | RA/PM  | 校验验收通过，置为只读         |

### 4.2 评审流程

1. 前置条件：需求处于“分析中”，且必填项完整；
2. RA 发起评审，系统生成评审单、保存需求快照，需求转为“待评审”；
3. 评审人提交意见（通过 / 需修改 / 反对），主持人提交结论；
4. 通过：需求转为“评审通过”，业务版本冻结为 `V1.0`，生成版本快照；
5. 驳回：需求转为“已驳回”，记录驳回原因，提出人修改后可重新提交。

本期实现为“主持人单点结论”，未强制校验全部评审人意见，属于简化项（见第 10 章）。

### 4.3 变更流程

1. 需求处于评审通过、已排期、开发中、测试中或待验收时，允许发起变更；
2. 变更单记录原因、内容、影响工时与影响描述；
3. 审批人（PM/ADMIN）通过或驳回；
4. 通过后由 RA 实施：业务版本递增（如 `V1.0 → V1.1`）、变更次数 +1、生成 JSON 快照；
5. 归档后不允许变更。

本期为单级审批，未实现“增量超过 8 小时需二级审批”。

### 4.4 交付与验收流程

| 里程碑    | 达成标准            | 责任角色  |
| ------ | --------------- | ----- |
| 需求评审通过 | 评审结论通过并进入排期池    | PM    |
| 开发完成   | 开发任务全部完成        | DEV   |
| 测试完成   | 测试结论通过          | QA    |
| 验收通过   | 验收单结论通过且必备交付物齐全 | 验收人   |
| 归档     | 验收通过、无未完成事项     | RA/PM |

发起验收时校验三类必备交付物：`需求规格说明书`、`测试报告`、`部署说明`。验收不通过必须填写返工要求，系统自动创建返工任务并把需求退回“开发中”，验收轮次 +1。

### 4.5 异常与边界

| 场景   | 处理规则                          | 状态变化              |
| ---- | ----------------------------- | ----------------- |
| 评审驳回 | 需求退回提出人修改，记录驳回原因              | 待评审 → 已驳回         |
| 需求挂起 | 记录挂起前状态 `hold_from_status`    | 任意在途状态 → 已挂起      |
| 恢复   | 回到挂起前状态，清空 `hold_from_status` | 已挂起 → 原状态         |
| 逾期   | 期望日期早于当前日期且未完成，只做标记，不自动改状态    | 状态不变              |
| 返工   | 验收不通过生成返工任务，重新走开发测试           | 待验收 → 开发中         |
| 归档只读 | 归档后编辑、变更、再验收均拒绝               | 返回 `40005`        |
| 并发冲突 | 后提交者乐观锁失败                     | 返回 `40007`，数据不被覆盖 |
| 越权访问 | 数据权限不通过                       | 返回 `403 / 20002`  |

## 6. 状态机

### 6.1 需求状态

共 14 个状态：草稿、待受理、分析中、待评审、评审通过、已排期、开发中、测试中、待验收、已验收、已归档、已驳回、已撤销、已挂起。

核心流转（完整表见 `RequirementFlowService`）：

| 当前状态 | 动作                | 目标状态 | 所需权限点                          |
| ---- | ----------------- | ---- | ------------------------------ |
| 草稿   | SUBMIT            | 待受理  | `requirement:submit`（且为提出人）    |
| 待受理  | ACCEPT            | 分析中  | `requirement:accept`           |
| 分析中  | SUBMIT_REVIEW     | 待评审  | `requirement:submit-review`（由评审单触发） |
| 待评审  | REVIEW_PASS       | 评审通过 | `requirement:review-decide`（由评审单触发） |
| 待评审  | REVIEW_REJECT     | 已驳回  | `requirement:review-decide`（由评审单触发） |
| 已驳回  | RESUBMIT          | 分析中  | `requirement:submit`（且为提出人）    |
| 评审通过 | SCHEDULE          | 已排期  | `requirement:schedule`         |
| 已排期  | START_DEV         | 开发中  | `requirement:develop`          |
| 开发中  | SUBMIT_TEST       | 测试中  | `requirement:submit-test`      |
| 测试中  | SUBMIT_ACCEPTANCE | 待验收  | `requirement:submit-acceptance`（由验收单触发） |
| 待验收  | ACCEPT_PASS       | 已验收  | `requirement:accept-decide`（由验收单触发） |
| 待验收  | ACCEPT_REJECT     | 开发中  | `requirement:accept-decide`（由验收单触发） |
| 已验收  | ARCHIVE           | 已归档  | `requirement:archive`          |
| 在途状态 | HOLD              | 已挂起  | `requirement:hold`             |
| 已挂起  | RESUME            | 原状态  | `requirement:hold`             |
| 未归档  | CANCEL            | 已撤销  | `requirement:cancel`           |

实现要点：

1. 前端只提交动作编码，目标状态由服务端计算；
2. 评审、验收结论只能由单据驱动，不能直接调用动作接口；
3. 挂起用 `hold_from_status` 记录原状态；
4. 每次流转写审计日志，详情页时间线由审计日志生成。

### 6.2 任务状态

| 当前状态            | 允许目标状态                            | 附加校验     |
| --------------- | --------------------------------- | -------- |
| TODO 待开始        | IN_PROGRESS / BLOCKED / CANCELLED | 阻塞需填原因   |
| IN_PROGRESS 进行中 | DONE / BLOCKED / CANCELLED        | 完成需填完成说明 |
| BLOCKED 已阻塞     | IN_PROGRESS / CANCELLED           | —        |
| DONE 已完成        | 终态                                | —        |
| CANCELLED 已取消   | 终态                                | —        |

### 6.3 评审、变更、验收

| 单据  | 状态                                      | 说明            |
| --- | --------------------------------------- | ------------- |
| 评审单 | PENDING → PASSED / REJECTED             | 主持人提交结论       |
| 变更单 | PENDING → APPROVED / REJECTED → APPLIED | 通过后实施生效       |
| 验收单 | PENDING → PASSED / FAILED               | 失败生成返工任务，轮次递增 |

## 8. 非功能需求

### 8.1 性能与容量

设计目标（**未做压测，上线前建议补 JMeter 证据**）：

| 指标              | 目标      | 当前状态 |
| --------------- | ------- | ---- |
| 登录接口 P95        | < 500ms | 未测量  |
| 列表查询 P95（10 万条） | < 1s    | 未测量  |
| 需求详情 P95        | < 800ms | 未测量  |
| 看板首屏            | < 3s    | 未测量  |
| 附件上传（20MB）      | < 10s   | 未测量  |

容量假设：需求 10 万、任务 50 万、审计日志 100 万，单表不分库分表。看板待办最多扫描 200 条在途需求，属于演示规模的约束。

### 8.2 安全

- 所有业务接口默认登录，仅登录、Swagger、静态资源匿名；
- 密码 BCrypt 加盐，连续 5 次失败锁定 15 分钟；
- JWT 2 小时有效，密钥支持环境变量注入；
- 功能权限 + 数据权限双重校验，越权不泄露数据是否存在；
- 上传校验后缀、大小，UUID 落盘，下载前校验数据权限；
- 审计日志只追加，不提供删除接口。

### 8.3 可靠性与一致性

- 业务动作使用事务，单据与状态同成败；
- 需求更新使用乐观锁，冲突返回 `409 / 40007`；
- 编号使用原子自增 + 独立事务，避免单机 `synchronized` 假设；
- 审计日志使用 `REQUIRES_NEW`，业务回滚仍保留失败痕迹；
- 统一异常处理，业务异常与系统异常分离，系统异常不返回堆栈。

### 8.4 可维护性与可测试性

- Controller 不写业务，Service 承担事务与编排，Mapper 只做数据访问；
- 统一响应、统一异常、统一错误码、统一审计切面；
- 33 个自动化用例覆盖状态机、数据权限、接口安全、并发冲突、编号并发与看板；
- 测试使用独立 H2 内存库，Flyway 自动建表与写入演示数据。

### 8.5 兼容性与部署

- JDK 21，兼容 17 LTS 基线；
- H2 默认免安装，MySQL 8 通过 profile 切换；
- Docker Compose 编排 MySQL、应用、Nginx；
- 浏览器面向桌面端 Chromium 内核，未做移动端适配。

### 8.6 易用性

- 中文界面，角色菜单按权限显隐；
- 列表有空状态与加载状态；
- 流程按钮由后端返回的 `availableActions` 驱动，避免展示不可用动作；
- 错误提示包含原因与下一步建议（如缺失字段逐项列出）。

## 10. 与设计蓝本的差异

| 蓝本内容         | 本期实现                         | 原因                                          |
| ------------ | ---------------------------- | ------------------------------------------- |
| 20 张表        | 20 张表                        | 未建独立工时表、通知表、评论表；新增评审参与人关联表                   |
| 42 条功能需求     | 43 条（35 条已实现、2 条部分实现、6 条未实现） | 保留 MVP + 部分标准版，裁掉通知、评论、Word 导出、部门/字典管理与两级审批 |

| 评审全员会签       | 主持人单点结论                      | 控制实现成本                                      |
